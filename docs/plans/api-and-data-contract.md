# Maintenance Mate — API and Data Contract

**Status:** Implementation-ready **proposal for all-five review; approval is pending.** SQLite is selected by the user. The field names, validation limits, reference format, strict status transitions, schema details, and response/error conventions below are proposed MVP choices—not evidence that all five members have approved them. Confirm this contract before implementation and record any agreed changes here.

## 1. Purpose, scope, and assumptions

Define one small contract for the Java/Javalin backend, browser page, domain/service/repository layers, and local persistence. The tracker is for **hostels generally**, not one university or institution.

- Local classroom demonstration using synthetic/demo data only; SQLite file persists requests across application restarts.
- Workflow: a resident submits a request; staff view the list and update status; a resident can look up a request by reference.
- No real login, identity verification, authorization, privacy, confidentiality, production security, or deployment claims. `User.canAccess(...)` is an OOP/polymorphism demonstration only; it is not an API security boundary.
- No contact details, resident names, photos, notifications, chat, emergency workflow, integrations, assignment route, pagination, or external-service dependency in this MVP.
- The API accepts only the request fields below. A browser form should use the same names and pass the JSON unchanged.

**Evidence/assumptions:** The canonical plan names Java/Javalin, five routes, the six domain classes, a simple web page, and restart persistence. The current untracked scaffold has a Maven `pom.xml` declaring Java source/target 17 and a hello-world `Main.java`; it does not yet declare application dependencies. Maven is not installed on the inspected machine, so this document does not claim that the scaffold builds or that any dependency/version has been tested.

## 2. Proposed request model

### Create input: `POST /api/requests`

| JSON field | Required? | Type and proposed validation | Meaning |
|---|---:|---|---|
| `hostelBlock` | Yes | String; trim leading/trailing whitespace; 1–100 characters after trimming | Hostel and, where applicable, block (for example, `Maple Hostel, Block B`). |
| `roomNumber` | Yes | String; trim; 1–30 characters after trimming | Room/unit label; kept as text to allow values such as `A-12`. |
| `description` | Yes | String; trim; 1–1,000 characters after trimming | Short repair description; no image or attachment. |

The body must be a JSON object with these three fields only. Missing, null, non-string, blank-after-trim, over-limit, malformed JSON, or unknown fields are rejected. Client-supplied `reference`, `status`, `assignedStaffId`, `createdAt`, or `updatedAt` are never accepted. No resident name, phone, email, password, or other personal data is required or stored.

### Server-managed fields and response representation

Every successful create/read/list/status response uses this shape:

```json
{
  "reference": "MM-7C2A91D4B60F",
  "hostelBlock": "Maple Hostel, Block B",
  "roomNumber": "A-12",
  "description": "The sink tap is leaking.",
  "status": "Received",
  "assignedStaffId": null,
  "createdAt": "2026-10-28T09:15:30Z",
  "updatedAt": "2026-10-28T09:15:30Z"
}
```

- `reference`: generated by the service; proposed exact format `MM-` plus 12 uppercase hexadecimal characters (`^MM-[0-9A-F]{12}$`). Generate from a UUID-derived value and retry if the repository reports a uniqueness collision. It is a lookup label, **not** a secret, password, or authorization token.
- `status`: server-controlled; begins as `Received`.
- `assignedStaffId`: nullable; starts as `null`. This is retained to map the accepted optional staff assignment in the domain model, but the MVP has no assignment endpoint and does not persist a staff/user directory.
- `createdAt`, `updatedAt`: server-generated UTC ISO-8601 instants (Java `Instant.toString()` format). Set equal on creation. On a successful status change, update only `updatedAt`; never trust client timestamps.
- On list responses, objects are ordered by `createdAt` descending, then `reference` ascending for ties. The MVP returns the full small demo dataset; pagination/filter parameters are not part of this contract.

### Statuses and proposed allowed transitions

Exact status strings (including capitalization):

1. `Received` — initial state, assigned by the server at creation.
2. `In Progress` — staff have started handling the request.
3. `Resolved` — work is recorded as complete.

Proposed strict forward-only transition graph: `Received → In Progress → Resolved`. No backward transition, skipped step, or repeated same-status update is allowed. A recognized status with a disallowed transition returns `409 STATUS_TRANSITION_CONFLICT`; an unrecognized or missing status value returns `400 VALIDATION_ERROR`. A successful transition updates `updatedAt` once. All-five review must explicitly confirm or amend this strictness before implementation.

## 3. SQLite persistence and domain mapping

**Selected store:** one local SQLite database; no file-store alternative. Proposed default path is `./data/maintenancemate.db` relative to the application working directory. Create the parent directory if absent. Use JDBC prepared statements and a transaction for writes; close connections/statements/results with try-with-resources. A restart/reload test must use the same database path. No ORM or migration framework is proposed: create the table and indexes with idempotent `CREATE TABLE/INDEX IF NOT EXISTS` at startup. If the schema later needs incompatible changes, stop and agree a deliberate reset/migration rather than silently discarding demo data.

```sql
CREATE TABLE IF NOT EXISTS maintenance_requests (
    reference        TEXT PRIMARY KEY NOT NULL
        CHECK (length(reference) = 15
               AND substr(reference, 1, 3) = 'MM-'
               AND substr(reference, 4) NOT GLOB '*[^0-9A-F]*'),
    hostel_block     TEXT NOT NULL
        CHECK (length(trim(hostel_block)) BETWEEN 1 AND 100),
    room_number      TEXT NOT NULL
        CHECK (length(trim(room_number)) BETWEEN 1 AND 30),
    description      TEXT NOT NULL
        CHECK (length(trim(description)) BETWEEN 1 AND 1000),
    status           TEXT NOT NULL
        CHECK (status IN ('Received', 'In Progress', 'Resolved')),
    assigned_staff_id TEXT NULL,
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_maintenance_requests_status
    ON maintenance_requests(status);
CREATE INDEX IF NOT EXISTS idx_maintenance_requests_created_at
    ON maintenance_requests(created_at DESC);
```

SQLite stores timestamps as UTC ISO-8601 text generated by the Java service. Primary-key uniqueness is the reference uniqueness constraint. The status check constrains persisted values; the service enforces transition rules. There is deliberately no users table or foreign key for `assigned_staff_id`: users are synthetic demo objects and authentication/assignment persistence are out of scope. Keep status updates atomic: update by `reference` and expected current status; if no row changes, re-read to distinguish missing request from a concurrent/disallowed transition.

### Responsibilities and encapsulation (six accepted classes)

| Class | Proposed private state / responsibility | Boundary |
|---|---|---|
| `User` | Abstract shared base; private synthetic `userId` and `displayName`; fixture-only contact value only if the class exercise requires it. Expose controlled getters/behavior, not writable public fields. | No credentials or verified identity. Do not accept or persist contact data through this API. A shared `canAccess(MaintenanceRequest)` may demonstrate polymorphism in unit tests only. |
| `Resident extends User` | Private `hostelBlock` and `roomNumber`; submits a request and can perform a reference lookup in the demo workflow. | Constructed with a synthetic fixture identity and validated request location; the API has no resident identity field and this does not identify a real person. |
| `MaintenanceStaff extends User` | Synthetic staff identity; views requests and asks the service to advance status. | No login, real actor attribution, staff directory, or public assignment route. |
| `MaintenanceRequest` | Private/final reference, resident/location, description, initial/updated status and timestamps; optional assigned `MaintenanceStaff`. Provide controlled construction and status-transition methods; do not expose setters that bypass rules. | Serializes through the API representation; repository maps its persisted scalar fields. `createdAt` and reference do not change after creation. |
| `RequestService` | Private repository dependency and reference generator. Validates/normalizes create input, creates the domain object, lists/finds by reference, enforces allowed transitions, sets timestamps, and delegates a lightweight storage-health check. | Routes call the service rather than implementing business rules or SQL. Throws the defined domain/application exceptions below. |
| `RequestRepository` | Private JDBC/database details. Save, list, find, atomically update status, and check database availability. Map rows to/from `MaintenanceRequest` and its `Resident`/optional staff representation. | Prepared statements only; no HTTP concerns and no status-transition policy. |

For row mapping, `hostel_block` and `room_number` populate the request's `Resident` location; any `User` identity used by the local demo remains synthetic and is not persisted as resident identity. A null `assigned_staff_id` maps to no assigned staff; if a synthetic assignment is used in a domain test, map its stored ID to a fixture `MaintenanceStaff`, not a real staff directory. There is deliberately no users table or foreign key. Use a `List<MaintenanceRequest>` for the API list and/or a `Map<String, MaintenanceRequest>` keyed by reference where a collection is needed in the domain/test path; persisted reads remain repository-owned. Keep any `User` polymorphism example synthetic and separate from claims about protecting endpoints.

## 4. HTTP and JSON conventions

- JSON property names are camelCase and match the tables above. Successful responses set JSON content type.
- Error envelope is always:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request data is invalid.",
    "details": { "fields": { "roomNumber": "Must not be blank." } }
  }
}
```

`details` is always an object; use `{}` when no safe field details apply. Validation field details map field names to short messages. Do not return stack traces, SQL, filesystem paths, or raw exception messages to the browser.
- Malformed JSON, wrong JSON root type, invalid path-reference syntax, and field validation errors return 400. A syntactically valid but absent reference returns 404. A valid status name that violates the transition graph returns 409. Unexpected application/storage failures are handled centrally and do not leak internals.
- A single Javalin exception-mapping layer catches domain/application exceptions and maps them to this envelope. Route handlers must not duplicate error serialization.

| Exception / condition | HTTP | Error code |
|---|---:|---|
| `InvalidRequestException` (body/path/field/status value invalid) | 400 | `VALIDATION_ERROR` |
| JSON parser exception (malformed JSON) | 400 | `MALFORMED_JSON` |
| `RequestNotFoundException` | 404 | `REQUEST_NOT_FOUND` |
| `InvalidStatusTransitionException` | 409 | `STATUS_TRANSITION_CONFLICT` |
| Generated reference still collides after bounded retry | 409 | `REFERENCE_CONFLICT` |
| `StorageUnavailableException` (SQLite unavailable) | 503 | `STORAGE_UNAVAILABLE` |
| Any otherwise unhandled exception | 500 | `INTERNAL_ERROR` |

For service-generated errors, the service throws the named exception; a central Javalin handler catches it and writes the corresponding status/envelope. Repository JDBC failures are wrapped as `StorageUnavailableException` (without returning database details). The JSON parser error is translated at the HTTP boundary. The final catch-all logs the exception server-side and returns only the generic 500 envelope.

## 5. Five route contracts

### 1) `POST /api/requests` — create

- **Request:** required JSON object with only `hostelBlock`, `roomNumber`, `description` as specified above.
- **Success:** `201 Created`; body is the complete request representation, with server-generated reference/timestamps, `status: "Received"`, and `assignedStaffId: null`. No Location header is required for the MVP.
- **Errors:** `400 MALFORMED_JSON` or `400 VALIDATION_ERROR`; `409 REFERENCE_CONFLICT` only if bounded reference-collision retries fail; `503 STORAGE_UNAVAILABLE` if SQLite cannot write; `500 INTERNAL_ERROR` otherwise.
- **Flow:** route parses JSON and calls `RequestService.create`; service validates and creates values, then calls `RequestRepository.save`. Service exceptions are mapped by the central handler; JDBC failures are wrapped and mapped as above.

### 2) `GET /api/requests` — list for staff demo page

- **Request:** no body; no query parameters in MVP.
- **Success:** `200 OK`, body `{ "requests": [<request representation>, ...], "count": <number> }`; list includes all three statuses and follows the documented stable order. The browser may filter the returned list locally.
- **Errors:** no input validation, not-found, or conflict case applies because the route has no user-controlled input. Return `503 STORAGE_UNAVAILABLE` on database read failure; `500 INTERNAL_ERROR` otherwise.
- **Flow:** route calls `RequestService.list`; service delegates to `RequestRepository.list`; repository returns domain objects and the API layer serializes them. No client filter silently changes the result.

### 3) `GET /api/requests/{reference}` — reference lookup

- **Request:** no body; path reference must match `MM-[0-9A-F]{12}` (case-sensitive).
- **Success:** `200 OK`, body is one complete request representation.
- **Errors:** `400 VALIDATION_ERROR` for malformed reference syntax; `404 REQUEST_NOT_FOUND` for a well-formed but absent reference; `503 STORAGE_UNAVAILABLE` on database read failure; `500 INTERNAL_ERROR` otherwise.
- **Flow:** route calls `RequestService.findByReference`; service validates the reference and throws `InvalidRequestException` or `RequestNotFoundException`; the central handler maps either exception. Repository owns the lookup SQL.

### 4) `PUT /api/requests/{reference}/status` — advance status

- **Request:** valid reference in path and JSON object with exactly one required field, `status`, whose value is one of the exact three status strings. Example: `{ "status": "In Progress" }`.
- **Success:** `200 OK`, body is the updated complete request representation. `updatedAt` is newly generated by the server; reference, request fields, and `createdAt` do not change.
- **Errors:** `400 MALFORMED_JSON` or `400 VALIDATION_ERROR` for invalid body/path/status; `404 REQUEST_NOT_FOUND` for a valid absent reference; `409 STATUS_TRANSITION_CONFLICT` for backward, repeated, or skipped transition; `503 STORAGE_UNAVAILABLE` on database update failure; `500 INTERNAL_ERROR` otherwise.
- **Flow:** route calls `RequestService.updateStatus`; service loads/checks the current state, enforces the transition graph, and asks the repository to compare-and-update atomically. It throws `InvalidStatusTransitionException` on a disallowed/raced update and `RequestNotFoundException` when absent. One central handler maps exceptions. A no-op/repeat status is a conflict, not a silent success.

### 5) `GET /api/health` — local health check

- **Request:** no body.
- **Success:** `200 OK`, body `{ "status": "ok" }` only when the application is running and `RequestRepository` can execute a lightweight SQLite availability check.
- **Errors:** no input validation, not-found, or conflict case applies because the route has no user-controlled input. Return `503 STORAGE_UNAVAILABLE` with the standard error envelope if SQLite is not available; `500 INTERNAL_ERROR` for an unexpected failure. Do not include paths or credentials in the response.
- **Flow:** route calls `RequestService.checkStorageHealth`; service delegates a lightweight SQLite availability check to the repository, which wraps database failures as `StorageUnavailableException`; the common handler maps it.

## 6. Compact example workflow

Create:

```http
POST /api/requests
Content-Type: application/json
```

```json
{
  "hostelBlock": "Maple Hostel, Block B",
  "roomNumber": "A-12",
  "description": "The sink tap is leaking."
}
```

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "reference": "MM-7C2A91D4B60F",
  "hostelBlock": "Maple Hostel, Block B",
  "roomNumber": "A-12",
  "description": "The sink tap is leaking.",
  "status": "Received",
  "assignedStaffId": null,
  "createdAt": "2026-10-28T09:15:30Z",
  "updatedAt": "2026-10-28T09:15:30Z"
}
```

Advance status:

```http
PUT /api/requests/MM-7C2A91D4B60F/status
Content-Type: application/json
```

```json
{ "status": "In Progress" }
```

Response: `200 OK` and the same representation with `status: "In Progress"` and a new server-generated `updatedAt`. A subsequent `PUT` to `Resolved` is valid; a direct `Received → Resolved` or repeated `In Progress → In Progress` returns `409 STATUS_TRANSITION_CONFLICT`.

## 7. Test-first acceptance checklist

Before accepting implementation, all five should review this contract and the implementers should drive each behavior RED → GREEN:

- [ ] Create rejects malformed JSON, missing fields, non-string values, blanks after trim, over-limit strings, and unknown/client-managed properties with the agreed 400 envelope.
- [ ] Create trims accepted strings, generates a unique-format reference and UTC timestamps, sets `Received`, persists all fields, returns 201, and does not accept caller-supplied reference/status/time.
- [ ] Restart the app against the same SQLite file; find and list the created request with unchanged reference/status/data/timestamps.
- [ ] Reference lookup distinguishes malformed reference (400) from well-formed missing reference (404); existing reference returns the agreed complete representation.
- [ ] List returns all rows in stable order and correct count; empty database returns `requests: []`, `count: 0`.
- [ ] `Received → In Progress` and `In Progress → Resolved` succeed; backward, skipped, and same-status transitions fail with 409 and leave persisted status unchanged.
- [ ] Status update changes only status and `updatedAt`; missing reference returns 404; invalid status returns 400.
- [ ] Database failures are centrally mapped to 503 without leaking SQL/path; unknown exception returns generic 500; error envelope shape is consistent.
- [ ] Health returns 200 only when the app and SQLite check succeed; unavailable SQLite yields 503.
- [ ] Browser form/list/reference lookup/status update use these exact fields, route paths, response shapes, and status/error behavior.
- [ ] Tests demonstrate the six class boundaries, private state/controlled updates, `Resident` and `MaintenanceStaff` inheritance, one meaningful polymorphic `User` call, and exception throw → catch → HTTP mapping without describing them as real security.
